USB CDC GDB Stub File Status
Date: 2026-05-04 (roadmap cross-ref 2026-05-14)

Purpose
- Record what is already implemented for the USB CDC GDB stub route and what still remains before it becomes a usable source-level debug path.

Roadmap / tasks (dual CDC, IDE wiring)
- See docs/DUAL_CDC_AND_USB_DEBUG_ROADMAP.md for the current design split (service CDC vs user CDC) and checklist.
- Single-cable USB pitfalls (EP0 STATUS, bootloader layout) live in docs/USB_SINGLE_CABLE_PLAN.md §「关键要点与易踩坑」.

Implemented

1. Boards menu and build profile surfaces
- File: hardware/arduinonrf/nrf52/boards.txt
- Status:
  - `menu.buildprofile.usbgdbstub` exists on native-USB nRF52840 boards.
  - The profile sets `-DNRF_BUILD_PROFILE=2 -DNRF_SYSTEM_USB_GDB_STUB=1`.
  - The profile is not present on `devboard_nrf52833`.

2. Platform recipes and IDE debug metadata
- File: hardware/arduinonrf/nrf52/platform.txt
- Status:
  - OpenOCD remains the default SWD debug path.
  - Stub-specific metadata now exists for transport name, default TCP target, bridge describe command, bridge list-ports command, and bridge launch command.
  - `debug.executable` remains the ELF produced by the selected build.

3. Runtime truth surface
- Files:
  - hardware/arduinonrf/nrf52/cores/arduino/NrfDebug.h
  - hardware/arduinonrf/nrf52/cores/arduino/NrfDebug.cpp
  - hardware/arduinonrf/nrf52/cores/arduino/NrfSystem.h
  - hardware/arduinonrf/nrf52/cores/arduino/NrfSystem.cpp
- Status:
  - `NrfDebugTransport::UsbCdcGdbStub` exists.
  - `usbDebugSupported()` reports true in the stub profile.
  - `probeRequired()` reports false in the stub profile.
  - Diagnostics expose `usb-cdc-gdbstub`.

4. Host bridge tool
- File: hardware/arduinonrf/nrf52/tools/niusrobotlab/usb_gdbstub_bridge.ps1
- Status:
  - The bridge script now supports:
    - `-Describe`
    - `-ListPorts`
    - TCP listener on loopback
    - serial-to-TCP and TCP-to-serial forwarding
  - This completes the host-side bridge entrypoint, but it still depends on a real firmware stub speaking the GDB remote protocol over USB CDC.

5. Validation coverage
- Files:
  - tools/release/validate_debug_profiles.ps1
  - tools/release/compile_matrix.ps1
- Status:
  - The debug profile validation script compiles `SystemLayerInfo` and `DebugPolicy` with `buildprofile=usbgdbstub`.
  - The debug profile validation script also compiles `UsbGdbStubBreakpoint` and `UsbGdbStubFault` with `buildprofile=usbgdbstub`.
  - The general compile matrix includes a native-USB board with the stub profile and those stub-specific examples.

6. Firmware trap runtime and exception ownership
- Files:
  - hardware/arduinonrf/nrf52/cores/arduino/NrfGdbStub.h
  - hardware/arduinonrf/nrf52/cores/arduino/NrfGdbStub.cpp
  - hardware/arduinonrf/nrf52/cores/arduino/Arduino.h
  - hardware/arduinonrf/nrf52/cores/arduino/wiring.cpp
- Status:
  - A minimal firmware-side GDB remote loop now exists for the stub profile.
  - The runtime captures the stacked exception frame plus callee-saved registers.
  - The runtime owns `HardFault_Handler`, `MemManage_Handler`, `BusFault_Handler`, `UsageFault_Handler`, and `DebugMon_Handler` in the stub profile.
  - The current packet set is intentionally minimal: stop reply, register read, memory read, detach, and continue.

7. USB CDC runtime binding and VS Code launch wiring
- Files:
  - .vscode/tasks.json
  - .vscode/launch.json
- Status:
  - The firmware stub polls and writes through the existing core USB CDC runtime.
  - The workspace now includes a bridge task and an external-target Cortex-Debug launch entry for `UsbGdbStubBreakpoint`.

Remaining

8. Runtime completeness gaps
- Remaining:
  - Add register write packets (`G`/`P`) and broader memory-map coverage.
  - Refine fault-resume handling for instructions that would immediately trap again after `continue`.
  - Decide whether to expose single-step support or keep MVP at stop/read/continue only.

9. Example and validation coverage
- Changes:
  - Run end-to-end live-device validation of `UsbGdbStubBreakpoint` and `UsbGdbStubFault` through the bridge.
  - Expand validation once write packets or step support are added.

10. IDE external-target integration
- Current state:
  - Platform metadata names the bridge and target endpoint.
  - The workspace provides a concrete external-target launch entry.
- Remaining:
  - Verify the launch flow on real hardware and adjust the adapter configuration only if Cortex-Debug needs stricter external-server options.

11. What should not be touched for MVP
- Do not replace existing SWD/OpenOCD upload or debug recipes.
- Do not change UF2 or DFU upload behavior.
- Do not claim support on nRF52833 or any non-native-USB board.

12. Recommended next implementation order
- First: `NrfGdbStub` core module with register frame capture and stop/continue.
- Second: USB CDC transport binding inside the runtime.
- Third: fault and breakpoint examples for validation.
- Fourth: exact IDE external-target launch plumbing.
- Fifth: memory access and breakpoint refinement.
